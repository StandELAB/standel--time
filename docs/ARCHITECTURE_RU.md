# StandEL Time v0.7 — техническая архитектура

**Статус:** пилотная серверная основа для дальнейшей разработки. Это не сертифицированная и не полностью протестированная система учёта часов для эксплуатации с персональными данными.

## Технологии
- Next.js 16 App Router + TypeScript, серверные маршруты на Vercel.
- Supabase PostgreSQL, Auth, Row Level Security; `@supabase/ssr` для браузерных cookies.
- Resend (отправка email-приглашения); Twilio (отправка SMS-приглашения) + настроенный SMS OTP-провайдер в Supabase Auth (можно Twilio).
- Регион Supabase: Europe / Stockholm eu-north-1 (выбор конкретного региона при создании проекта).
- Домен: standeltime.se, *не подтверждён и не зарегистрирован*.

## Потоки пользователей
### Администратор
1. Создаёт проекты и назначения. Добавляет сотрудника через `/admin` → «Приглашения».
2. `POST /api/admin/invitations` проверяет его сессию и `org_members.role='admin'` в БД.
3. Сервер создаёт **неподтверждённого** пользователя Supabase Auth через секретный серверный ключ.
4. Сервер создаёт криптографический токен 256 бит, записывает только SHA-256, контакт, назначенную роль и срок 48 часов.
5. Отправляет ссылку по Resend/Twilio. В случае ошибки отправки ссылка отзывается; пользователь в Auth пока остаётся — это следует очищать по отдельной задаче.

### Работник
1. Получает ссылку `/join?token=...`.
2. Запрашивает OTP на **тот же** email/телефон. Supabase Auth закрыт для обычной регистрации (`Allow new users to sign up: OFF`), а приложение использует `shouldCreateUser:false`.
3. Подтверждает OTP, получает Supabase сессию.
4. Сервер вычисляет SHA-256 от токена и вызывает SQL-функцию `claim_invitation` от имени пользователя.
5. Транзакция проверяет `auth.uid`, совпадение подтверждённого адреса/телефона, срок, отзыв и одноразовость, а затем создаёт `org_members` и помечает токен использованным.

### Повторный вход
Email или SMS OTP на `/login`; после входа — только назначенная роль и права RLS. Важный момент: для email код в Supabase email template должен содержать `{{ .Token }}`, а не только magic link; в рабочем проекте нужен собственный SMTP.

## Основные таблицы
- `organizations` — компания.
- `org_members` — сотрудники, роли, бригадир, статус.
- `projects`, `project_assignments` — объекты и назначения.
- `project_rates` — тарифы клиента, скрытые от работников.
- `time_entries` — часы, объекты, метод manual/timer, regular/overtime/ob; вычисляемые часы; запрет пересечений.
- `absences` — болезни, личные причины, отпуска и статусы заявок.
- `shifts` — рабочие графики.
- `certificates` — ID06, Lift, Fallskydd, SSG.
- `invitations` — серверные приглашения и хеши токенов.
- `audit_events` — журнал изменений часов и активаций приглашений.

## Разграничение доступа
| Действие | Работник | Бригадир | Администратор |
|---|---|---|---|
| Смотреть свои часы, календарь | Да | Да | Да |
| Добавлять свои часы | Да | Да | Да |
| Смотреть часы команды | Нет | Назначенной команды | Всей компании |
| Видеть чужие сертификаты | Нет | Нет | Да |
| Добавлять объекты, назначения, приглашения | Нет | Нет | Да |
| Ставки клиента | Нет | Нет | Да |

RLS и серверные проверки обязательны. Скрытые кнопки НЕ заменяют авторизацию. **Не выдавайте публично `SUPABASE_SECRET_KEY`** — он обходит RLS.

## Важные особенности / что не готово
- Cloud-пилот v0.7 демонстрирует вход, приглашения, создание объектов/назначений, ввод часов, заявки, графики и простой CSV. **Не все интерфейсные возможности локальной v0.6 перенесены:** цветной XLSX, месячные сводки, полноценный удобный календарь, редактирование с подтверждением, экспорт payroll, уведомления на телефон и финансовые отчёты требуют дополнительной реализации.
- В пилоте таймер использует время браузера и теряет незавершённую смену при закрытии вкладки. Для эксплуатации нужен серверный таймер с событиями и идемпотентностью.
- Данные нельзя массово переносить из `localStorage` без ревизии, сопоставления сотрудников и проектов.
- На уровне БД есть исключающие ограничения перекрывающихся смен, но ещё нужен атомарный механизм для проверки гонок между больничными и временем.
- `time_entries` пока разрешают работнику менять свои записи (все изменения логируются). Перед go-live нужно: закрытие расчётных периодов, отдельное разрешение работодателя на исправление исторических часов и неизменяемое журналирование.
- Приглашения на уже существующий пользовательский контакт, повторная отправка, ручной отзыв, смена телефона/email и управление ролями через UI не реализованы. Админ-пользователь создаётся вручную при первичной настройке.
- SMTP, SMS OTP, rate limits, CAPTCHA, MFA для администраторов, тестирование восстановления из бэкапа и GDPR-документация обязательны перед реальной работой.
- Для описания болезни не нужно запрашивать диагноз; ограничьте хранение мединформации.
- Прозрачно уведомляйте работников о том, кто имеет доступ к часам и как исправления фиксируются, даже когда административный интерфейс не виден в их приложении.

## Минимальные тесты перед запуском
1. Неприглашённый пользователь не может получить членство и доступ к данным.
2. Ссылка для другого email/телефона не активируется, истёкшая и повторная ссылка отклоняется.
3. Работник A не видит / не меняет часы B, даже при ручном REST-запросе с ID B.
4. Бригадир видит только назначенную ему команду, не видит тарифы.
5. Нельзя записать два пересекающихся интервала одному человеку на одну дату.
6. Все часы сохраняются после перезагрузки и на другом устройстве после входа.
7. Экспорт показывает верные часы и не включает данные другого клиента.
8. Отработать резервное копирование и восстановление на отдельный проект.
9. Провести независимый security review SQL RLS и серверных маршрутов.
